# DEV-TEST-01 — E2E autenticado reproducible

## Objetivo
Establecer y validar una suite E2E autenticada, reproducible y aislada para login, selección de negocio, permisos, scoping y dashboard, con PostgreSQL efímero separado de cualquier base de desarrollo o producción.

## Scope

**Incluye**

- Infraestructura PostgreSQL E2E independiente, identificable y destruible sin afectar `lucem_retail` ni otra base existente.
- Setup determinista de tres usuarios ficticios (`ADMIN`, `SELLER`, `INVENTORY_MANAGER`), dos negocios, memberships, categorías, productos, variantes, stock y ventas suficientes para comprobar el dashboard.
- Flujos reales mediante `POST /api/auth/login`, `POST /api/businesses/select` y `POST /api/auth/logout`; las respuestas, redirects, cookies httpOnly y expiración son parte del contrato observado.
- Generación de estados de sesión por Playwright desde el login real, en archivos temporales ignorados, sin cookies manuales, tokens fabricados, acceso directo a la tabla `Session` para autenticar ni bypass de guards.
- Pruebas API/integración/browser de autenticación, cambio de negocio, matriz de permisos, aislamiento por negocio, dashboard con datos y estados recuperables, logout y capturas en `1440x768`, `768x1024` y `390x844`.
- Limpieza de datos creados por E2E únicamente dentro de la base E2E y sólo después de las pruebas; la limpieza debe ser idempotente y conservar el entorno ajeno intacto.
- Documentación de comandos, variables no versionadas, evidencia, estados `PASS`, `FAIL` o `BLOCKED` y el warning de seguridad vigente.

**Fuera de alcance y prohibiciones**

- No usar el `.env` del desarrollador, las credenciales demo del README, `americanoutfit`, `demo-norte`, la base `lucem_retail`, un servidor PostgreSQL compartido ni datos de producción.
- No modificar `docker-compose.yml`, `.env.example`, Prisma schema, migraciones, auth, API o producto como parte del Planner; los cambios de implementación que el Generator necesite deberán estar limitados al trabajo DEV-TEST-01 y conservar estos límites.
- No invocar `GET /api/audit` en ningún test, setup, smoke, fixture, navegador o script. Debe permanecer documentado literalmente: `GET /api/audit exposes passwordHash`. Este riesgo impide declarar producción lista.
- No poner contraseñas, `DATABASE_URL`, cookies, tokens, `storageState`, dumps de DB, capturas con secretos ni artefactos Playwright bajo Git.
- No fabricar una sesión con SQL, Prisma, `context.addCookies`, `document.cookie`, headers de autenticación inventados o mocks del login cuando el criterio requiere integración real. Los mocks sólo pueden aislar un error de UI y deben estar etiquetados como fixture, nunca como PASS autenticado.
- No usar `GET /api/businesses` como sustituto del flujo de selección: el cambio real debe comprobar `POST /api/businesses/select` con `{ businessId }` y su redirect.

## User flows

1. **Preflight y guardas** — Registrar `git rev-parse HEAD`, rama y `git status --short` sin imprimir secretos. Exigir `DATABASE_URL` explícito desde un archivo/variable local no versionado, con nombre de base exacto `lucem_retail_e2e`, puerto dedicado `55432` o equivalente, usuario E2E dedicado y host local/CI controlado. Rechazar antes de conectar si la URL contiene `lucem_retail`, `production`, `prod`, `staging`, un host no permitido, el puerto compartido `5432`, o no contiene el marcador `lucem_retail_e2e`. Resolver la URL y el nombre de DB en el proceso de setup y abortar si falta cualquier guardia.
2. **PostgreSQL independiente** — Preferir un contenedor efímero del proyecto `lucem-retail-e2e`, volumen `lucem-retail-e2e-pg` y base `lucem_retail_e2e`, por ejemplo `docker run --rm --name lucem-retail-e2e-db -e POSTGRES_USER=lucem_e2e -e POSTGRES_PASSWORD=<valor-local-no-commiteado> -e POSTGRES_DB=lucem_retail_e2e -p 55432:5432 postgres:16-alpine`. Esperar readiness con `pg_isready`, aplicar sólo migraciones existentes (`npx prisma migrate deploy`) y nunca apuntar el proceso a la base del `docker-compose.yml` de desarrollo. Si Docker/daemon/PostgreSQL/readiness/migración no está disponible, detener la suite con `BLOCKED: E2E PostgreSQL unavailable` e incluir comando y salida de diagnóstico; no ejecutar contra otra DB ni degradar a mocks.
3. **Dataset determinista** — En el setup E2E, limpiar primero sólo registros cuyo namespace sea `DEV-TEST-01` dentro de la DB ya validada, crear dos negocios reservados `dev-test-01-centro` y `dev-test-01-norte`, usuarios con emails `dev-test-01-admin@invalid.test`, `dev-test-01-seller@invalid.test` y `dev-test-01-inventory@invalid.test`, y una contraseña efímera común proveniente de variable no versionada. Crear memberships: ADMIN en ambos negocios, SELLER sólo en Centro e INVENTORY_MANAGER sólo en Centro. Crear categorías/productos/variantes con SKU prefijado `DEV-TEST-01-`, una variante con stock 0, una con stock bajo y al menos dos variantes vendibles; crear ventas confirmadas y líneas en Centro con folios deterministas y ningún dato personal real. Toda escritura de preparación debe pasar las mismas guardas de DB.
4. **Login API real** — Usar un `APIRequestContext` o la página contra el servidor levantado con el `DATABASE_URL` E2E. `POST /api/auth/login` debe recibir `{ email, password }` una vez por usuario/estado, devolver `200`, usuario ficticio, negocios permitidos y `/negocios` para ADMIN o `/dashboard` para usuarios con un solo negocio. Verificar que sin credenciales válidas devuelve `401` sin sesión útil y que no se siguen redirects falsos. No leer ni registrar el valor de la cookie.
5. **Storage state Playwright** — Desde el login real, guardar `storageState` en una ruta temporal bajo `test-results` o `/tmp`, fuera de Git, separada por rol/negocio y creada por Playwright. La suite debe comprobar que el archivo existe sólo durante la ejecución, no incluirlo en artefactos persistentes y no insertar cookies manualmente. El setup debe renovar el estado ejecutando nuevamente el login real cuando la sesión de 30 minutos esté próxima a expirar o en cada corrida CI; nunca extenderla editando el archivo o la DB.
6. **Selección de negocio** — Con el `storageState` de ADMIN, abrir `/negocios`, mostrar exactamente Centro y Norte, seleccionar Norte y enviar `POST /api/businesses/select` con el ID real; comprobar `200`, `{ redirect: '/dashboard' }`, navegación a `/dashboard` y que `GET /api/dashboard` queda scopiado a Norte. Repetir Centro y comprobar que el cambio se refleja. Probar un ID inventado y un negocio no perteneciente al usuario: ambos deben ser rechazados (`403` o contrato equivalente) sin cambiar el negocio activo.
7. **Permisos y aislamiento API** — Con estados reales, comprobar login y `/api/dashboard` permitidos para cada rol con membership; comprobar que SELLER no puede endpoints de administración/inventario no permitidos, INVENTORY_MANAGER no puede acciones de venta no permitidas y ningún rol accede a una operación fuera de su matriz. No asumir permisos: derivarlos de `Role` y de los route handlers existentes. Solicitudes sin sesión deben devolver `401`. Nunca consultar audit para probar permisos.
8. **Aislamiento browser** — Navegar con ADMIN en Centro y Norte y comparar catálogo, stock, ventas y métricas: los registros de un negocio no deben aparecer en el otro. Verificar también que SELLER e INVENTORY_MANAGER sólo ven el negocio de su membership. Un `id` de producto, venta o variante de otro negocio debe devolver `403`, `404` o el contrato seguro existente, nunca datos del registro ajeno.
9. **Dashboard con datos** — En cada negocio aplicable, esperar `GET /api/dashboard` real y verificar status, parámetros y JSON `{ gross, net, units, cogs, profit, outOfStock, lowStock, recent }`. Comparar las métricas visibles con el dataset conocido, incluyendo al menos una venta, COGS/utilidad, alerta de agotado, alerta de bajo stock y hasta cinco ventas recientes. No llamar `GET /api/audit` ni sustituir la respuesta por fixture.
10. **Estados del dashboard** — Controlar una respuesta pendiente para comprobar skeleton/estado de carga sin ceros inventados; usar sólo una respuesta controlada, identificada como fixture, para `empty` (`recent: []`, métricas en cero) y error/reintento. El error debe ser accesible y no sensible; `Reintentar` debe emitir otro `GET /api/dashboard` sin mutar datos y recuperar el estado real. Las fixtures no cuentan como evidencia de negocio, auth, permisos o aislamiento.
11. **Logout y renovación** — Desde cada sesión browser, usar el control existente y enviar `POST /api/auth/logout`; verificar `200`, desaparición de la sesión al solicitar `/dashboard` y redirect a `/login`. Renovar con login real, no con cookies manuales. El cleanup no debe usar logout como sustituto de limpieza de DB.
12. **Responsive y capturas** — Ejecutar browser tests autenticados en `1440x768`, `768x1024` y `390x844`; capturar login, selector cuando aplique, shell/dashboard con datos, negocio alterno y logout/redirect. Cada artefacto debe indicar rol, negocio, URL, viewport, HEAD y si la respuesta fue real o fixture; medir `scrollWidth <= clientWidth`, foco visible, nombres accesibles, controles de al menos `44x44px` y ausencia de secretos.
13. **Cleanup y cierre** — Tras pasar/fallar la suite, ejecutar cleanup sólo si la guardia confirma la misma URL E2E y el namespace DEV-TEST-01. Borrar sesiones, ventas, líneas, movimientos, productos, categorías, memberships y usuarios/negocios E2E mediante relaciones seguras o una transacción; verificar que no quedan filas con el prefijo. Si falla la guardia, no borrar nada y marcar `BLOCKED`. Detener y eliminar el contenedor/volumen E2E sólo cuando sea propiedad de esta corrida; nunca detener procesos o contenedores ajenos.

## Modelo de datos

- Se conserva el schema Prisma actual y la migración `prisma/migrations/0001_init/migration.sql`; el aislamiento es de infraestructura y dataset, no un nuevo modelo paralelo. `DATABASE_URL` del proceso bajo prueba apunta exclusivamente a PostgreSQL E2E.
- **Identidad y tenancy:** `User(id, email, name, passwordHash, active)`, `Business(id, name, timezone, currency)`, `Membership(userId, businessId, role, canCancelSales)` y `Session(userId, activeBusinessId, tokenHash, expiresAt, lastActivityAt)`. Relaciones: usuario y negocio se unen por membership; session mantiene usuario y negocio activo. La única autenticación permitida para E2E es la ruta que crea `Session` y cookie httpOnly.
- **Catálogo:** `Category(businessId, name, active)`, `Product(businessId, categoryId, name, location, archived)` y `ProductVariant(businessId, productId, sku, barcode, size, color, cost, price, promoPrice, stock, lowStockThreshold, active)`. Cada fixture pertenece a un solo negocio; SKU y nombres de cleanup llevan `DEV-TEST-01-`.
- **Inventario:** `InventoryMovement(businessId, variantId, userId, type, quantity, reason, referenceType, referenceId)`. El setup puede crear el movimiento `INITIAL` mediante el mecanismo de datos E2E autorizado, y la validación debe comprobar stock y scoping.
- **Ventas:** `Sale(businessId, userId, folio, status, paymentMethod, subtotal, total, receivedAmount, changeAmount)` y `SaleLine(saleId, variantId, quantity, unitPrice, unitCost, lineTotal)`, con folio único por negocio. Las ventas deterministas de Centro deben producir dashboard no vacío; Norte debe tener un dataset deliberadamente distinto o vacío para demostrar aislamiento. `SaleIdempotency` sólo se crea si el contrato de venta la requiere.
- **No usados para evidencia:** `Return`, `Reservation`, `PriceCostHistory` y `AuditLog` no son necesarios para DEV-TEST-01. El login/logout puede escribir auditoría internamente, pero queda prohibido leer `GET /api/audit`; la advertencia `GET /api/audit exposes passwordHash` se conserva y cualquier suite que lo invoque falla el criterio de seguridad.
- La limpieza respeta foreign keys y elimina sólo entidades con IDs/emails/SKU/nombres del namespace E2E. No usa `TRUNCATE` global, no elimina tablas compartidas y no toca el seed demo.

## Stack y decisiones técnicas

- Mantener Next.js `15.3`, React `19`, TypeScript, Prisma `6.7`, PostgreSQL `16-alpine`, `bcryptjs`, Vitest y Playwright `1.51`; no añadir dependencias para sustituir auth ni instalar un servidor de sesión alternativo.
- El proceso web se ejecuta como en `playwright.config.ts` en `127.0.0.1:3101`; el servidor recibe el mismo `DATABASE_URL` E2E validado. `reuseExistingServer` queda deshabilitado en CI o se debe rechazar un servidor existente con una configuración de DB desconocida.
- Variables obligatorias, sólo en `.env.e2e`/entorno CI no versionado: `DATABASE_URL=postgresql://.../lucem_retail_e2e?schema=public`, `E2E_DATABASE_NAME=lucem_retail_e2e`, `E2E_DATABASE_PORT=55432`, `E2E_TEST_PASSWORD`, y, si aplica, `E2E_DB_CONTAINER`. `.env.e2e` debe permanecer ignorado; no se imprime su contenido. `SESSION_SECRET` de E2E también es efímero y distinto del desarrollo.
- Comandos reproducibles, sujetos a las guardas: `docker version`/`docker info`; levantar PostgreSQL E2E; `npx prisma migrate deploy`; `npx prisma generate`; ejecutar setup/fixtures E2E; `CI=1 npm run test:e2e -- --reporter=list`; cleanup; y retirar el contenedor. Calidad complementaria: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`.
- El setup se ejecuta una vez por worker/corrida, espera readiness, usa transacciones/orden determinista y produce estados Playwright. La suite usa `test.use({ storageState })` o proyecto `setup` de Playwright, no `addCookies`; los archivos se eliminan al terminar y se conservan sólo traces/screenshot sanitizados de fallos.
- API/integración usa requests same-origin y comprueba método, payload, status y aislamiento. Browser usa navegación visible y accesibilidad. Interceptar sólo errores/estados de UI expresamente marcados; no interceptar login, selección, logout, dashboard de datos ni permisos reales.
- Fallback obligatorio: si Docker no está instalado, `docker info` falla, el puerto dedicado está ocupado, `pg_isready` no alcanza la DB, `prisma migrate deploy` falla o la URL no pasa las guardas, el resultado global es `BLOCKED` con `BLOCKED: E2E PostgreSQL unavailable`, comando, código de salida y causa. No se usan el `docker-compose.yml` compartido, la DB actual, el seed demo ni mocks para convertirlo en PASS.

## Assumptions

- `DATABASE_URL` es la variable que Prisma consume en runtime; el valor E2E reemplaza al del entorno sólo para el proceso E2E y nunca se versiona. `DATABASE_URL_E2E` puede ser una fuente de configuración, pero el proceso debe recibir finalmente `DATABASE_URL` explícito y validado.
- La migración existente es la fuente de schema. El seed demo del README (`Demo123!`, `americanoutfit`, `demo-norte`) no es seed E2E porque es upsertable, no crea ventas deterministas y apunta al entorno compartido.
- Las contraseñas ficticias se generan o inyectan desde CI/local no versionado; se usan sólo en el request de login y nunca aparecen en logs, snapshots, URLs, capturas o commits.
- ADMIN tiene dos memberships para hacer observable `/negocios`; SELLER e INVENTORY_MANAGER tienen una membership para hacer observable el redirect directo a `/dashboard`. Si una guardia existente requiere otro permiso, la matriz se documenta con el role real, no se relaja el guard.
- La renovación de sesión se hace por el endpoint legítimo de login y genera un nuevo `storageState`; editar expiración, token o cookie convierte el criterio en FAIL. Un estado expirado debe producir redirect/login y no se repara con SQL.
- Las escrituras de login/logout/auditoría que la aplicación realiza son aceptables dentro de la DB E2E, pero no autorizan consultar `GET /api/audit`. El warning `GET /api/audit exposes passwordHash` sigue siendo obligatorio y producción no se declara lista.
- Capturas de estados interceptados se etiquetan `fixture`; sólo capturas con login, selección, dashboard y permisos contra PostgreSQL E2E real pueden probar integración autenticada.
- Si el entorno no puede proveer Docker/PostgreSQL independiente, la conclusión correcta es BLOCKED, no FAIL de producto ni ejecución contra una base compartida. La evidencia mínima es la salida del preflight y el criterio no se cuenta como PASS.

## Rubric de evaluación

Todos los criterios son binarios: `PASS` exige toda la evidencia indicada, `FAIL` contradice el contrato y `BLOCKED` sólo aplica cuando falta la infraestructura/autorización imprescindible. Cada resultado registra comando, fecha, HEAD, URL/endpoint, rol, negocio y artefacto. Un `BLOCKED` nunca cuenta como `PASS`.

1. **Guardas y DB aislada** — El preflight rechaza una URL insegura y acepta sólo `lucem_retail_e2e` en el puerto/host dedicado; `docker info`, readiness y `npx prisma migrate deploy` terminan correctamente sin tocar `lucem_retail`. Si no hay Docker/PostgreSQL, se documenta el fallback exacto `BLOCKED: E2E PostgreSQL unavailable`.
2. **Dataset determinista** — Una ejecución limpia crea exactamente los tres usuarios ficticios, dos negocios, memberships de roles definidos, catálogo con SKU namespace, stock 0/bajo/vendible y ventas/líneas reproducibles; una segunda ejecución produce el mismo resultado sin duplicados.
3. **Login real** — Playwright/API envía una sola vez el POST legítimo con credencial ficticia, comprueba status/payload/redirect y cookie httpOnly de sesión sin imprimirla; credenciales inválidas reciben `401` y no acceden a dashboard.
4. **Storage state seguro** — Cada rol/negocio autenticado usa `storageState` generado por Playwright fuera de Git, sin `addCookies`, `document.cookie`, token fabricado ni sesión SQL; el archivo se elimina al cierre y una renovación por login real funciona.
5. **Selección real** — ADMIN ve Centro/Norte y `POST /api/businesses/select` recibe exactamente el ID seleccionado, devuelve el redirect legítimo y cambia el negocio activo; un ID ajeno/inventado no cambia sesión y devuelve rechazo seguro.
6. **Matriz de permisos** — Los tres roles pueden ejecutar sólo sus rutas permitidas y reciben `401/403` según corresponda para rutas no permitidas; la matriz se comprueba con requests reales y no con `GET /api/audit`.
7. **Aislamiento de negocio** — Cambiar entre Centro/Norte cambia catálogo, stock, ventas y dashboard; ningún producto/venta/variante ajeno aparece en API o browser y un ID cross-business no filtra datos.
8. **Dashboard contractual** — `GET /api/dashboard` real devuelve el contrato actual y la UI muestra valores coincidentes para gross/net/units/cogs/profit, agotados, bajo stock y recientes, con máximo cinco ventas.
9. **Estados y reintento** — Una carga pendiente muestra estado accesible sin datos inventados; fixtures explícitas cubren vacío/error, `role=alert` es accionable y retry repite sólo GET. Las fixtures no se presentan como datos reales.
10. **Logout** — El control existente emite `POST /api/auth/logout`, devuelve éxito, invalida el acceso posterior y lleva a `/login`; no se simula logout borrando storage state antes de comprobar la ruta.
11. **Responsive desktop** — A `1440x768` el dashboard autenticado real no tiene overflow horizontal, conserva shell/navegación y la captura identificada contiene negocio, rol, URL y HEAD sin secretos.
12. **Responsive tablet/móvil** — A `768x1024` y `390x844` no hay overflow, recorte ni overlay indebido; foco/nombres accesibles funcionan y los controles interactivos miden al menos `44x44px`; existen capturas reales identificadas.
13. **Cleanup seguro** — Cleanup elimina sólo el namespace DEV-TEST-01 dentro de la DB E2E, puede repetirse sin error, deja cero filas del namespace y no modifica la DB/volumen/contendedor ajeno; una guardia fallida bloquea el borrado.
14. **No audit y seguridad** — La búsqueda de requests/traces confirma cero invocaciones a `GET /api/audit`; el SPEC/evidencia conserva literalmente `GET /api/audit exposes passwordHash`, no hay secretos en artefactos y no se declara producción lista.
15. **Calidad reproducible** — `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` y el comando Playwright permitido terminan en código 0, o cada excepción tiene salida exacta y estado `BLOCKED`; no se usa el seed demo ni una base compartida para ocultar un fallo.
