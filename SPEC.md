# DEV-DEPLOY-03 — Quick Tunnel público

## Objetivo
Publicar temporalmente la aplicación Lucem Retail mediante un Cloudflare Quick Tunnel oficial, conservando autenticación, roles y aislamiento de datos propios de Lucem y sin alterar el acceso LAN ni n8n.

## Scope
Incluye preparar y, sólo tras superar los bloqueos críticos, habilitar un Quick Tunnel efímero hacia exclusivamente el origen web Lucem existente; servicio `systemd` con reinicio supervisado; mecanismo verificable para obtener la URL vigente; controles antiabuso para registro, login y uploads; validación externa independiente; y backup/restauración operativa. La baseline de código es `1b9c63a728ea59fd21685e99f03e8216617e2de2`, ya publicada en `feature/lucem-ui-redesign-v1`. El HEAD de trabajo `e1527d8` preserva SPEC/FINDINGS anteriores bajo nombres `*.pre-DEV-DEPLOY-03.md`; mantener esos archivos intactos.

No configurar `--allowed-mail`, Cloudflare Access, dominio propio, DNS, allow-list de correos ni autenticación por Cloudflare. No publicar la base de datos, n8n, SSH u otro servicio; no abrir puertos del router/firewall ni cambiar puertos, bind LAN, Compose/volúmenes, configuración de staging o recursos n8n. No convertir en públicos los datos: enlace alcanzable públicamente significa que cualquier visitante puede llegar a la pantalla, pero datos y operaciones requieren la cuenta/sesión Lucem, membresía y rol correspondientes; todas las consultas y medios permanecen limitados al negocio autenticado.

Bloqueo crítico previo a cualquier arranque: registro masivo sin rate-limit ni antiabuso, protección insuficiente de login por IP, origen de IP falsificable/no verificable, o ausencia de cuota global de uploads/disco impiden iniciar túnel. No se aceptan mitigaciones sólo documentales. El límite de login actual en `src/lib/auth.ts` es cinco fallos/email/15 min en Map en memoria, pierde estado al reiniciar y no comparte estado entre procesos; `/api/auth/register` crea usuarios ilimitadamente y el upload sólo limita cada imagen a 5 MiB. Inspeccionar y cerrar estos riesgos antes de abrir exposición externa.

## User flows
1. El operador verifica rama/baseline y estado de servicios en modo de sólo lectura; valida recursos, espacio y backup existente de DB y `public/uploads/products`, sin leer ni imprimir secretos. Confirma por identificadores que PostgreSQL, app LAN y n8n permanecen sin cambios. Si estado o backup no son demostrables, detenerse sin despliegue.
2. El operador aplica controles de aplicación antes del túnel: límite de registro por IP y controles de abuso; límite de login por IP además del existente por email; respuestas limitadas (429 y `Retry-After`) y límites/métricas persistentes o con comportamiento deliberadamente documentado ante restart. Límites deben sobrevivir abuso distribuido razonable y no degradar el login válido entre emails. Limitar tamaño de request, cantidad/bytes totales de imágenes por negocio y un presupuesto global de almacenamiento con fallo cerrado; carga excedida devuelve 413/429 y no deja archivo parcial. Definir umbrales conservadores y configurables para beta, con rechazo por defecto si cuota/configuración no está disponible. CAPTCHA/correo no se presupone disponible; no habilitar registro público si los controles verificables no bastan para riesgo de spam.
3. La selección de IP cliente para rate-limit no confía en `X-Forwarded-For` ni en forwarded headers arbitrarios. Usar sólo señal de cliente emitida por Cloudflare en solicitudes que se demuestre que llegaron por el túnel. El origen LAN sigue accesible directamente y un cliente LAN puede falsificar headers Cloudflare; por tanto la señal no autentica proxy ni elimina bypass. No permitir una ruta directa desde WAN, no confiar en headers para autorización/identidad, y documentar que límites por IP pueden ser evadidos desde el origen LAN. Si no es posible distinguir solicitudes tunnel de acceso directo de modo seguro, o probar que ninguna ruta WAN llega al origen, riesgo crítico: no abrir Quick Tunnel. El login Lucem, cookie y controles CSRF/host existentes siguen siendo obligatorios.
4. Instalación/configuración aprobada de `cloudflared` oficial del sistema sin token de túnel ni credenciales de cuenta: iniciar Quick Tunnel sobre `http://192.168.1.117:3000` (o la dirección LAN exacta confirmada en runtime). Configuración/service target debe tener una única ruta/origen Lucem y no comodines a otros puertos. `systemd` reinicia el cliente si cae; registrar estado y errores sin secretos. La URL `*.trycloudflare.com` es volátil: se extrae de la salida/log de arranque de la instancia actual de cloudflared y se presenta como vigente sólo si servicio está activo y esa URL responde; tras restart/caída puede cambiar. No registrar la URL como permanente, no prometer hostname estable ni guardar URL antigua como actual. Procedimiento para localizarla: consultar `systemctl status`/journald del unit específico de cloudflared, identificar la URL `https://…trycloudflare.com` del último arranque exitoso, después comprobar status activo y HTTPS externo; sin coincidencia única y respuesta válida declarar “URL no disponible”, no inferir ni inventar. Los logs excluyen tokens, cookies, datos de negocio y credenciales.
5. Evaluador externo abre la URL HTTPS vigente en navegador/curl sin cookies: páginas de login/registro son alcanzables por TLS de Cloudflare edge, APIs/datos protegidos responden 401 y redirigen al login según contrato. Prueba registro controlado sólo si antiabuso fue aprobado, login correcto, sesión, logout, roles y separación entre dos negocios; nunca imprimir ni persistir cookies/tokens. Verifica no-cache/sensibilidad, imágenes privadas, 429, límites de carga y que headers arbitrarios no alteren IP/proxy ni autorización. Repetir desde otra IP si disponible. Sin operaciones comerciales sobre datos reales.
6. Si cualquier control falla, detener únicamente el unit de Quick Tunnel, comprobar que la URL deja de responder y conservar servicio/puerto LAN, DB, uploads, n8n y firewall intactos. Si pasa, informar URL como efímera junto con hora/estado del servicio, método seguro para recuperarla y comportamiento ante restart.

## Modelo de datos
No se requieren cambios de esquema Prisma para este despliegue. Se preservan modelos existentes `User(id, email UNIQUE, name, passwordHash, active, createdAt, updatedAt)`, `Business(id, name, branchName, giro, timezone, currency)`, `Membership(id, userId, businessId, role, canCancelSales)` con relación única usuario-negocio y `Role` (`ADMIN`, `SELLER`, `INVENTORY_MANAGER`), y `Session(id, userId, activeBusinessId, tokenHash UNIQUE, expiresAt, lastActivityAt)`. PasswordHash y tokenHash nunca se devuelven al cliente. Cada lectura/escritura usa el `businessId` asociado a la sesión y membresía; no se expone dato de un negocio por conocer su ID.

Uploads existentes son archivos en `public/uploads/products`, nombrados con id de negocio y UUID y servidos por endpoint autenticado; máximo actual por archivo 5 MiB, formatos JPEG/PNG/WebP/GIF. Se requiere cuota por negocio y global con contabilidad fiable de bytes/archivos y reconciliación segura frente a archivos huérfanos; puede implementarse en filesystem/configuración existente sin migration, pero especificar mecanismo y atomicidad antes del deploy. El filesystem/volumen de uploads debe persistir y tener espacio libre suficiente, umbral de reserva y alertas; al umbral crítico, rechazar escrituras, nunca llenar disco silenciosamente. No almacenar uploads en una ruta dentro del túnel distinta del origen.

Rate-limit no está actualmente persistido en Prisma. Seleccionar almacenamiento que sobreviva reinicios y opere con un único host; incluir claves, ventanas, contadores, expiración y límite de cardinalidad; no almacenar IP/email en logs en claro más tiempo del estrictamente necesario. Si se elige in-memory, registro público no es aceptable y no iniciar exposición bajo carga/reinicio. Las cuotas y límites configurados deben ser auditables sin revelar secretos.

## Stack y decisiones técnicas
Aplicación existente: Next.js `^15.3.0`, React `^19.0.0`, Prisma `^6.7.0`, PostgreSQL 16 Alpine, Node runtime para handlers de upload. No actualizar dependencias ni modificar stack comercial salvo controles indispensables y compatibles con versiones actuales. Entorno operativo documentado en `docs/deployment/LINUX-STAGING.md`, backup en `docs/deployment/BACKUP-RESTORE.md`, migraciones en `docs/deployment/POSTGRESQL-MIGRATIONS.md`; el documento previo de Tunnel es sólo referencia histórica y sus instrucciones de Access/dominio no aplican a esta tarea.

Cloudflare Quick Tunnel oficial con `cloudflared tunnel --url http://<origen-LAN-validado>` sin `--allowed-mail`, sin hostname propio ni configuración de cuenta. Definir unit dedicado de `systemd` con usuario/permisos mínimos, reinicio limitado con backoff, salida identificable por journal, aislamiento de target, sin shell que filtre secretos. No poner datos sensibles en argumentos, Environment, Git o logs. No implementar proxy alternativo ni cambiar listener de Next.js.

Rutas existentes a validar: `GET /login`, `GET /registro`; `POST /api/auth/register`, `POST /api/auth/login`, logout; `GET/POST /api/businesses`; upload `POST /api/products/image`, lectura `GET /api/products/image/[filename]`. El registro actual crea usuario y sesión en una sola llamada, login aplica limitación por email en memoria. Las rutas de imágenes requieren sesión y alcance negocio. Conservar cookies Secure en producción, HttpOnly, SameSite=Lax, CSRF, comprobaciones de rol y aislamiento. Para IP, aceptar únicamente una cabecera Cloudflare identificada y validada en ruta proveniente del túnel; rechazar spoof de `X-Forwarded-For`; no presentar `CF-Connecting-IP` como confiable para llamadas directas LAN. Límites de cuerpo multipart se hacen cumplir antes de cargar contenido completo a memoria/disco y tanto en reverse proxy/handler como filesystem.

Comandos de verificación desde raíz: `npm run lint`, `npm run typecheck`, `npm test -- --run`, `npm run build`, `npx prisma validate` con URL dummy local no sensible; Playwright existente `npm run test:e2e:security`, suites auth/dev-10 y pruebas dirigidas de uploads/cuotas. Evaluador externo usa `curl`/Playwright contra la URL recién leída de journal, sin `-v`, sin guardar Set-Cookie y con datos de prueba aislados. Verificar `systemctl is-active` y URL HTTPS; inspeccionar sólo estado/identificadores/redes/puertos de recursos pertinentes. Crear backup verificable antes de tocar el runtime; rollback sólo detiene unit Quick Tunnel y revierte cambios de app necesarios, no restaura ni borra DB/volúmenes salvo daño confirmado y autorización.

## Assumptions
- Quick Tunnel es público y temporal, no requiere cuenta, dominio o DNS y Cloudflare termina TLS en el edge; el origin hacia cloudflared puede ser HTTP en LAN/local. TLS edge no significa que los datos de Lucem sean públicos ni que exista cifrado extremo a extremo hasta el listener HTTP.
- No usar `--allowed-mail`, Access, lista de correo ni autenticación externa. El propio login de Lucem, registro, sesión, roles y tenant son la barrera de aplicación. Cualquier visitante puede intentar registro; sólo se habilita registro abierto después de antiabuso probado y límites de recursos. Si no se demuestra el control, el deploy queda bloqueado, no se reemplaza por Access ni se inventa una allow-list.
- URL Quick Tunnel puede cambiar cada arranque/reconexión y el proceso puede detenerse o ser rate-limited por Cloudflare. `systemd` mejora reinicio del proceso pero no garantiza permanencia, URL fija, SLA ni que reinicio preserve la dirección. Comunicar URL sólo tras recuperar la de la instancia vigente y comprobarla desde Internet.
- Cloudflare agrega cabeceras a solicitudes tunelizadas, pero el origin puede recibir solicitudes directas desde LAN; headers Cloudflare falsificados en esas solicitudes son posibles. No hay identidad criptográfica inferible sólo de la cabecera. El modelo de rate-limit no trata la IP reportada como autorización, y fallo al establecer frontera confiable es bloqueo crítico.
- El host tiene recursos compartidos y estado de staging previamente reportado; no asumir disponibilidad de disco, versión runtime, IP de origen, permiso de instalación ni configuración de systemd a partir de documentación. Descubrir valores operativos no secretos mediante inspección no mutante; no leer `.staging/config`, contraseñas, tokens, cookies, backups ni contenido comercial.
- Preservar `SPEC.pre-DEV-DEPLOY-03.md` y `FINDINGS.pre-DEV-DEPLOY-03.md`; único archivo producido por Planner es este `SPEC.md`.

## Rubric de evaluación
Cada criterio vale PASS sólo si se adjunta resultado observable reproducible con comando del proyecto, `curl` o Playwright; falta de evidencia, falla o riesgo crítico = FAIL/BLOCKED y no se publica URL. Evaluación en el baseline indicado, anotando HEAD/cambios requeridos y sin incluir valores secretos.

1. **Baseline/preservación:** `git rev-parse 1b9c63a` devuelve `1b9c63a728ea59fd21685e99f03e8216617e2de2`; rama `feature/lucem-ui-redesign-v1`; `git show --stat e1527d8` confirma archivado SPEC/FINDINGS; archivos `*.pre-DEV-DEPLOY-03.md` permanecen íntegros.
2. **Revisión y health sin secretos:** quedan identificados por estado/ID app, DB, listener LAN, uploads y n8n antes/después; backup DB/uploads previo se verifica por existencia, tamaño/checksum o procedimiento aprobado sin leer ni imprimir contenido secreto; si no se demuestra, no procede.
3. **Tunnel aislado:** inspección del unit/config/runtime muestra exactamente un target al origin Lucem validado; no destino/route hacia Postgres, n8n, SSH u otro puerto; PostgreSQL continúa sin puerto publicado y `n8n_server` conserva ID, estado y listener 5678.
4. **No cambio de exposición de red:** puerto/bind LAN original y regla firewall siguen iguales antes/después; no hay regla global, port-forward ni publicación nueva salvo ruta efímera cloudflared; prueba externa al origin IP/puerto falla desde WAN si verificable.
5. **URL actual reproducible:** `systemctl is-active <unit>` es `active`; una URL única `https://….trycloudflare.com` se obtiene del último arranque exitoso en journal sin tokens; `curl` HTTPS sin credenciales recibe respuesta válida; en restart/URL distinta se documenta la URL nueva y la anterior no se presenta como vigente.
6. **TLS y anonimato correcto:** `curl -I https://<URL-vigente>/login` y `/registro` negocian TLS válido y devuelven páginas alcanzables; `GET /api/businesses` anónimo y cualquier API de negocio devuelve 401; no se afirma que HTTP hacia origin sea TLS extremo a extremo.
7. **Auth y tenant propios:** Playwright/curl verifica cuenta de prueba registra/login/logout; cookie es Secure, HttpOnly, SameSite=Lax en HTTPS; rol insuficiente recibe 403 y negocio ajeno 404/no datos; dos negocios de prueba no cruzan datos ni imágenes; no se usan cookies reales ni se imprimen Set-Cookie.
8. **Registro antiabuso:** Playwright o script de requests repite registro con IP de prueba dentro de ventana configurada; umbral produce 429/Retry-After, no crea usuarios/sesiones extra y reintento posterior a expiración tiene comportamiento especificado. Configuración/estado persiste al restart o prueba documentada confirma alternativa de bloqueo; ausencia de protección verificable = FAIL crítico.
9. **Login antiabuso:** fallos por IP y por email quedan limitados; al superar ventana responde 429 con Retry-After sin validar contraseñas/crear sesiones; otro usuario legítimo no queda bloqueado por ataques dirigidos a email ajeno; spoof `X-Forwarded-For` no evade límite. Prueba cruza restart/estado, y rate limiting no reside únicamente en Map por proceso.
10. **Límite de confianza IP:** prueba con headers arbitrarios (`X-Forwarded-For`, Host, Proto) no cambia identidad/origin ni evade reglas. Sólo solicitudes efectivamente tunnelizadas usan cliente Cloudflare verificado para cuota; acceso directo LAN no se trata como proxy confiable. Si no puede distinguirse, riesgo se declara y túnel queda sin iniciar.
11. **Límite de upload por request:** requests con archivo permitido de hasta 5 MiB JPEG/PNG/WebP/GIF responden 201 autenticado/admin autorizado; anónimo 401, formato/tipo inválido y tamaño excedido se rechazan; cuerpo sobredimensionado no se materializa íntegro en memoria/disco ni deja archivo parcial.
12. **Cuotas de almacenamiento:** Playwright/curl alcanza cuota por negocio y límite global configurados, obtiene rechazo explícito, bytes/archivos no aumentan, otro tenant no consume cuota atribuible ajena y al cruzar umbral de disco se falla cerrado antes de agotar volumen. Persistencia/reconciliación y disponibilidad libre se verifican sin leer archivos comerciales.
13. **Sin spam/recursos ilimitados:** prueba de abuso automatizada de registro y carga no crea volumen ilimitado de User, Session o archivos ni hace crecer almacenamiento más allá de cuota; controles aplican también con muchas direcciones/email simuladas según threat boundary documentada. Si quedan bypasses prácticos críticos, publicación FAIL.
14. **Protección de privacidad:** respuestas anónimas no contienen usuario, negocio, productos, ventas, inventario ni detalles de DB; logs de app/systemd no contienen contraseña, sesión, cookie, token, contenido upload o PII innecesaria; imágenes se entregan sólo al usuario autenticado del negocio dueño.
15. **Unit lifecycle y reversión:** `systemctl status`/journal muestran arranque, restart con backoff y error legible sin secreto; parar sólo el unit de túnel hace que Quick URL deje de responder y app LAN siga respondiendo; DB/uploads/n8n no se reinician ni mutan.
16. **Calidad:** pasan `npm run lint`, `npm run typecheck`, `npm test -- --run`, `npm run build`, `npx prisma validate` y suites Playwright auth/security/uploads pertinentes; las E2E usan DB aislada y cleanup prueba cero residuos, nunca staging con datos comerciales.
17. **Bloqueos críticos y reporte:** antes de start existe evidencia de rate-limit registration/login, cuota de disco/uploads, frontera de IP entendida y backup verificado; si cualquiera falla, service permanece parado y no se divulga URL. Si todos pasan, informe indica URL y hora de verificación como temporal, estado de unit y método de recuperar URL tras restart; sin dominio estable ni promesa de disponibilidad.
