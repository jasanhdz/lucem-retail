# DEV-02 — Dashboard operativo

## Objetivo
Implementar `/dashboard` como un tablero operativo real, responsive y accesible dentro del `WorkspaceShell` existente, usando los datos de `GET /api/dashboard` y la dirección visual Stitch sin duplicar el shell ni modificar auth, DB o backend.

## Scope

**Incluye**

- Reemplazar únicamente el `PreparationPlaceholder` de `app/(workspace)/dashboard/page.tsx` por la vista dashboard de DEV-02, manteniendo `app/(workspace)/layout.tsx` como única frontera de autenticación y `WorkspaceShell` como único shell persistente.
- Consumir `GET /api/dashboard` con `fetch`, incluyendo `from` y `to` sólo si se implementa un selector de periodo. El contrato actual devuelve `gross`, `net`, `units`, `cogs`, `profit`, `outOfStock`, `lowStock` y `recent`; tratar importes serializados como dinero y no recalcular cifras con datos inventados en el cliente.
- Presentar una jerarquía operativa clara: título y periodo, métricas de ventas netas/unidades/COGS/utilidad, alertas de inventario agotado y bajo, y ventas recientes con folio, importe, estado y fecha. Los nombres pueden adaptarse al espacio disponible, pero cada valor debe corresponder al contrato real.
- Aplicar la composición visual de las referencias Stitch relevantes: `diseno/pantalla_c_shell_de_aplicaci_n_web_escritorio/{screen.png,code.html}` para el shell desktop, `diseno/pantalla_d_navegaci_n_m_vil_web_responsiva/{screen.png,code.html}` para navegación móvil, y los sistemas `diseno/retail_operational_clarity/DESIGN.md` y `diseno/retail_pos_inventory_system/DESIGN.md` para tokens, tipografía, superficies, estados y objetivos táctiles. La pantalla C/D es autoridad de composición; no copiar un HTML aislado ni introducir CDN.
- Mantener navegación, negocio activo, usuario, CTA Nueva venta, menús y navegación inferior en `WorkspaceShell`/`MobileBottomNavigation`. El dashboard sólo ocupa `.workspace-content`; no renderiza otro sidebar, topbar, bottom bar, `<html>`, `<body>` ni instancia alternativa de `WorkspaceShell`.
- Implementar estados distinguibles y accesibles: carga con skeletons de dimensiones estables, vacío cuando todas las métricas/listas aplicables estén sin datos, error de red o HTTP con mensaje accionable y botón Reintentar, y éxito con datos reales. No convertir un `401` en estado vacío: la guarda del layout sigue redirigiendo a `/login`.
- Adaptar y probar 1440px, 768px y 390px de ancho sin overflow horizontal: grilla de métricas y secciones legible en desktop/tablet, composición apilada y controles táctiles en móvil, respetando safe-area y la navegación existente.
- Añadir o actualizar pruebas y estilos mínimos necesarios para esta vista, sin cambiar contratos existentes ni instalar dependencias. Los roles posteriores documentarán la entrega en `docs/ui-redesign/DEV-02-DASHBOARD.md` y consolidarán resultados en `FINDINGS.md`; esos documentos no son entregables de este Planner.

**Fuera de alcance**

- No cambiar `app/api/**`, `src/lib/auth*`, `src/lib/db*`, Prisma schema, migraciones, seed, sesiones, permisos, servicios de dominio, endpoints, dependencias, infraestructura o configuración de despliegue.
- No crear un endpoint dashboard nuevo ni consultar endpoints no existentes. El dashboard usa `GET /api/dashboard`; sólo podrá usar otro endpoint si el contrato ya existe en el checkout y la necesidad queda justificada en la documentación posterior. No ejecutar mutaciones.
- No implementar filtros, exportación, gráficas, drill-down, edición de inventario, ventas, auditoría ni acciones nuevas que no estén soportadas por contratos existentes. Un selector de fechas es opcional y, si se incluye, sólo cambia `from`/`to` del endpoint existente.
- No rehacer el shell, duplicar controles globales, restaurar la UI legacy ni modificar ningún asset bajo `diseno/`. No afirmar que las referencias Stitch son evidencia de una sesión autenticada.
- No hacer login real, crear sesiones, usar credenciales del README, seed, migrar, escribir en DB ni llamar `GET /api/audit`. El resultado no puede declararse listo para producción mientras persista el warning conocido `GET /api/audit exposes passwordHash`.

## User flows

1. **Entrada autenticada** — La guarda existente de `app/(workspace)/layout.tsx` ejecuta `getAuth()`; sin sesión redirige a `/login`. Con sesión y negocio activo, monta una sola `WorkspaceShell` y entrega el dashboard como `children`. El usuario ve el contexto de negocio, navegación actual, CTA Nueva venta y el título Resumen sin shell duplicado.
2. **Carga inicial** — Al montar la vista, ejecutar `GET /api/dashboard` con `credentials: 'same-origin'`; mientras espera, mostrar skeletons con roles/labels accesibles y no mostrar ceros como datos cargados. Si se usa periodo, enviar `?from=YYYY-MM-DD&to=YYYY-MM-DD` y conservar el intervalo visible.
3. **Dashboard con datos** — Ante `200`, validar defensivamente la forma esperada, formatear importes en `MXN` de forma consistente con el negocio y renderizar neto, unidades, COGS, utilidad, agotados, bajo stock y hasta cinco ventas recientes. Cada tarjeta debe tener nombre accesible, valor visible y, cuando exista, contexto de periodo; la lista reciente no debe inventar enlaces o acciones.
4. **Dashboard vacío** — Ante `200` con métricas cero y `recent: []`, mostrar un estado vacío explícito y útil, diferenciado de carga/error, sin insertar ventas ficticias. Las alertas con cero elementos deben comunicar que no hay alertas, no ocultar silenciosamente la sección requerida.
5. **Error recuperable** — Ante error HTTP, JSON inválido o rechazo de red, mostrar `role="alert"` con mensaje no técnico y un botón Reintentar con nombre accesible. Reintentar debe volver a solicitar `GET /api/dashboard`, limpiar el error al iniciar y no mutar datos. No exponer stack traces, tokens o respuestas sensibles.
6. **Cambio de periodo opcional** — Si se implementa, el usuario selecciona un rango válido, el control anuncia el cambio y dispara un nuevo GET con `from`/`to`; fechas inválidas no generan request y muestran validación. El botón o control de periodo mide al menos 44×44px y funciona con teclado. Si no se implementa, usar el periodo por defecto del endpoint y documentar esa decisión.
7. **Responsive y navegación** — A 1440px el dashboard comparte el ancho útil del shell y conserva la densidad Stitch; a 768px reorganiza columnas sin recortes; a 390px apila contenido, mantiene textos/valores legibles, deja la navegación inferior operable y no crea scroll horizontal. Navegar a otra ruta y volver no debe dejar overlays, listeners o skeletons pendientes.
8. **Documentación posterior** — El rol Generator/implementador registra en `docs/ui-redesign/DEV-02-DASHBOARD.md` rutas modificadas, contrato usado, decisiones visuales, estados, viewports, capturas y comandos ejecutados. El rol Evaluator agrega a `FINDINGS.md` los criterios numerados con PASS/FAIL/BLOCKED y evidencia; ningún rol debe presentar una captura fixture como sesión real.

## Modelo de datos

- No se agregan tablas, campos, tipos, relaciones ni migraciones. El modelo consumido es el existente y el aislamiento por negocio lo garantiza el servidor mediante `getAuth()`.
- `GET /api/dashboard` acepta opcionalmente `from: string` y `to: string` en formato `YYYY-MM-DD`; por defecto calcula el día actual. El cliente debe conservar ambos límites como rango de presentación, sin cambiar timezone ni contrato.
- Respuesta exitosa existente: `{ gross: string, net: string, units: number, cogs: string, profit: string, outOfStock: number, lowStock: number, recent: RecentSale[] }`.
- `RecentSale` existente: `{ id: string, folio: number, total: string, status: 'CONFIRMED' | 'CANCELLED', createdAt: string }`. `total` es decimal serializado y `createdAt` es fecha serializada; formatear sin usar `id` como texto visible salvo necesidad de accesibilidad.
- La ruta calcula ventas confirmadas del `Business` activo a partir de `Sale` y `SaleLine`, devoluciones del periodo desde `Return`, variantes activas de `ProductVariant` para existencias y ventas recientes. Las relaciones relevantes son `Business` → `Sale`, `Return`, `ProductVariant`; `Sale` → `SaleLine`.
- Los datos de ausencia son válidos: no asumir que una lista no vacía existe, no convertir `null`/forma inválida en éxito y no mostrar `passwordHash`, sesiones, membresías privadas ni datos de auditoría.

## Stack y decisiones técnicas

- Mantener Next.js 15, React 19, TypeScript, CSS existente en `app/styles/`, `lucide-react` y Playwright/Vitest ya instalados. No añadir librerías de gráficas, iconos, fechas o comparación visual.
- La página permanece en `app/(workspace)/dashboard/page.tsx`; componentes específicos reutilizables pueden vivir en `src/components/` sólo si reducen duplicación real. Los estilos dashboard pueden añadirse a `app/styles/workspace.css` o a un archivo importado por `app/globals.css`; no alterar la arquitectura del shell.
- Usar un componente cliente sólo para fetch, estados, reintento y controles interactivos; mantener la guarda server-side intacta. `GET` debe usar same-origin cookies y no registrar respuestas o datos personales en consola.
- Preferir HTML semántico (`main` provisto por shell, headings, `section`, `ul`/`table` cuando corresponda), `aria-live`/`role="status"` para carga y `role="alert"` para error, foco visible, orden de tabulación lógico y `prefers-reduced-motion`. Todos los controles interactivos deben tener al menos 44×44px.
- Usar tokens existentes y la jerarquía visual de Stitch: Plus Jakarta Sans para títulos, Inter si ya está establecido para datos densos, fondo neutral claro, superficies blancas, bordes sutiles, verde profundo para acción/estado positivo y ámbar/rojo sólo para alertas semánticas. Contraste mínimo WCAG AA para texto y controles.
- Capturas posteriores deben realizarse con Playwright en 1440×900, 768×1024 y 390×844, usando una sesión autorizada proporcionada por el entorno o un fixture claramente rotulado. Comparar cada captura con la referencia Stitch aplicable mediante la herramienta de comparación disponible en el proyecto, registrar viewport, URL, baseline, salida y discrepancias; no llamar al endpoint de auditoría.
- Comandos de verificación del proyecto: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` y `CI=1 npm run test:e2e -- --reporter=list`. Los E2E nuevos deben interceptar sólo respuestas controladas para estados, o usar datos de una sesión autorizada sin mutaciones; no depender de credenciales documentadas.

## Assumptions

- `/dashboard` seguirá bajo el layout workspace actual; no se crea una ruta paralela ni una composición que vuelva a pintar `WorkspaceShell`.
- El contrato actual de `GET /api/dashboard` es la fuente de verdad y el backend no se corrige en DEV-02, incluso si su semántica de COGS/devoluciones difiere de otros reportes. Las diferencias deben registrarse como finding, no ocultarse con cálculos client-side.
- Los importes se muestran en MXN porque `Business.currency` actualmente tiene ese valor por defecto y el endpoint no devuelve moneda; no se introduce conversión. Si el checkout existente expone otra convención de formato, reutilizarla sin ampliar el contrato.
- El periodo por defecto del endpoint es suficiente para el primer corte; el Generator decidirá explícitamente si implementa selector `from`/`to`, sin inventar periodos comparativos ni porcentajes.
- La referencia desktop C describe principalmente el shell, por lo que sus dimensiones, navegación y jerarquía se respetan; la información del dashboard se compone con el sistema Stitch, no se atribuye a una pantalla histórica que no exista.
- Las capturas autenticadas requieren autorización del entorno. Sin ella, los criterios de integración visual pueden quedar BLOCKED; una fixture no-auth sólo sirve para composición y debe llevar marca visible, nunca contar como datos reales.
- Documentar después de implementar: `docs/ui-redesign/DEV-02-DASHBOARD.md` es responsabilidad del Generator/implementador y la actualización de `FINDINGS.md` es responsabilidad del Evaluator. Este Planner sólo reemplaza `SPEC.md`.
- El warning obligatorio de seguridad permanece: `GET /api/audit exposes passwordHash`. No se declara producción lista aunque lint, tests o build pasen.

## Rubric de evaluación

Todos los criterios son binarios: **PASS** sólo con todas las condiciones observables; **FAIL** si una condición contradice la evidencia o falta una verificación ejecutable; **BLOCKED** únicamente cuando falta una sesión autorizada imprescindible, indicando la evidencia ausente. Registrar comando, URL, fecha, viewport y artefacto en `docs/ui-redesign/DEV-02-DASHBOARD.md`; no contar BLOCKED como PASS.

1. **Sólo dashboard implementado** — `git diff --name-only` del implementador muestra cambios de la vista/estilos/pruebas/documentación autorizados, no `SPEC.md` adicional; `app/(workspace)/dashboard/page.tsx` ya no exporta `PreparationPlaceholder` y no se modifican API, auth, Prisma, migraciones, dependencias o infraestructura.
2. **Shell único** — Con Playwright en 1440×900 y 390×844, `/dashboard` muestra exactamente un elemento de navegación principal, un topbar y una navegación móvil según breakpoint; inspección de DOM confirma que la página no monta `WorkspaceShell`, sidebar, topbar ni bottom navigation propios.
3. **Contrato real** — Un test de red autenticado o fixture de respuesta controlada observa `GET /api/dashboard` con cookies same-origin, comprueba status `200` y verifica que los valores visibles de al menos `net`, `units`, `profit`, `outOfStock` y una venta `recent` coinciden con el JSON recibido; no se usan datos hardcodeados.
4. **Aislamiento y seguridad de datos** — La inspección del endpoint y una prueba HTTP confirman que el dashboard sólo usa datos del negocio autenticado; no llama `GET /api/audit`, no expone `passwordHash`, tokens o secretos en HTML, consola, capturas o documentación, y el warning literal `GET /api/audit exposes passwordHash` queda documentado junto con la declaración de no producción.
5. **Carga estable** — Un E2E intercepta el GET pendiente y verifica skeleton/status accesible, ausencia de métricas falsas y ausencia de salto estructural apreciable; al liberar la respuesta, desaparece el estado de carga y aparecen datos reales.
6. **Éxito completo** — Con payload no vacío, E2E verifica título, periodo, métricas de ventas netas/unidades/COGS/utilidad, conteos de agotados/bajo stock y lista reciente con folio, total, estado y fecha; todos los números coinciden con la respuesta y el texto es legible.
7. **Vacío inequívoco** — Con `200` y métricas cero/`recent: []`, E2E verifica un estado vacío identificable que no contiene ventas ficticias, no se confunde con skeleton/error y comunica correctamente la ausencia de alertas o actividad.
8. **Error y reintento** — Con una primera respuesta HTTP no exitosa o rechazo de red, E2E verifica `role="alert"`, mensaje accionable sin detalles sensibles y botón Reintentar; al responder `200`, el mismo flujo recupera el dashboard sin recarga completa ni request mutante.
9. **Periodo, si existe** — Si la UI incluye selector, E2E verifica que rango válido produce `GET /api/dashboard?from=...&to=...`, que se actualizan datos y que rango inválido no solicita; si no existe, la documentación registra explícitamente la decisión de usar el periodo por defecto y el criterio pasa por esa ausencia intencional.
10. **Responsive 1440/768/390** — Capturas Playwright en 1440×900, 768×1024 y 390×844 verifican `scrollWidth <= clientWidth`, no recortes de títulos/valores, orden legible de secciones y navegación existente operable; los controles interactivos miden al menos 44×44px.
11. **Comparación visual Stitch** — Para cada viewport se guardan capturas identificadas y una comparación reproducible contra `pantalla_c_shell_de_aplicaci_n_web_escritorio/screen.png` o `pantalla_d_navegaci_n_m_vil_web_responsiva/screen.png`, más los tokens DESIGN.md; el comando/herramienta, baseline, resultado y diferencias de composición se registran. PASS exige que shell, jerarquía, espaciado, superficies, tipografía y navegación sean consistentes; no se acepta “se ve bien” sin captura/comparación.
12. **Accesibilidad** — E2E/inspección verifica headings en orden, nombres accesibles de botones, `role=status`/`role=alert`, foco visible por teclado, navegación sin ratón, contraste WCAG AA de texto/controles, `prefers-reduced-motion` y ausencia de iconos como único significado.
13. **Navegación preservada** — Desde `/dashboard`, Playwright activa Nueva venta, una ruta visible del sidebar y el menú móvil sin duplicación ni overlays residuales; la URL cambia a destinos existentes y volver a dashboard conserva el shell único.
14. **Checks de calidad** — `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` y el E2E DEV-02 terminan con código 0, o cada excepción queda registrada como BLOCKED con salida exacta; no se ejecutan login real, seed, migración ni mutaciones.
15. **Documentación y límites** — Existe `docs/ui-redesign/DEV-02-DASHBOARD.md` con contrato, estados, viewports, capturas/comparaciones, comandos y limitaciones, y `FINDINGS.md` contiene evaluación binaria por criterio, findings abiertos y la advertencia de seguridad; ningún documento afirma producción lista ni sesión real cuando sólo hubo fixture.
